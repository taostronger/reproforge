# 需求分析

> ReproForge 要解决什么问题、服务谁、提供哪些能力。

## 1. 背景与问题

在 Web 应用开发与测试中，**Bug 复现**是一项高频却低效的工作：

- **复现成本高**：测试员发现 Bug 后，要手工编写回归测试、反复试错定位最小复现路径，耗时且依赖经验。
- **口述难落地**：测试员能口述「我点了什么、应该怎样、实际怎样」，但这些自然语言难以直接转化为可运行、可回归的工程产物。
- **经验不沉淀**：每次复现都是一次性的，相似的 Bug 反复出现却无法参考历史，重复劳动。
- **多模态信息浪费**：截图、录屏、语音口述里藏着大量线索，但传统流程只取文字描述，视觉与语音信息被丢弃。

ReproForge 的出发点：**让大模型理解 Bug（从口述 / 截图 / 操作里提取意图），让 Playwright 证明 Bug（真实回放、连跑判稳定、求最小复现），并把过程沉淀为可记忆、可回归的产物。**

## 2. 目标

构建一个**多模态 Bug 复现与回归智能体**，输入「截图 / 视频 / 语音 + 操作 + 口述」，输出：

1. 一份**可运行的 Playwright 回归测试**（带断言，连跑稳定）；
2. 一条**最小复现路径**（删冗余步骤后的最短稳定复现序列）；
3. 一份**可交付的 Markdown Bug Issue**（预期 / 实际 / 复现步骤 / 稳定率 / 可疑代码）；
4. （可选）**历史相似 Bug 参考**与**可疑代码文件排序**。

## 3. 目标用户

| 用户 | 诉求 | ReproForge 提供 |
|---|---|---|
| 测试工程师 | 快速把口述 Bug 变成可回归测试 | 多模态输入 → 自动生成 Playwright 测试 + 最小复现 |
| 开发工程师 | 拿到最小步骤快速复现 / 修复 | 最小复现路径 + 可疑文件排序 + 稳定率 |
| 团队 | Bug 经验沉淀、相似问题参考 | RAG 记忆库，新 Bug 检索历史相似案例 |

## 4. 典型场景

**场景 A：商城优惠券 Bug（主演示场景）**
用户输优惠码 `SALE20` 应用（总价 80），改数量 2 后总价仍 80（应为 160）。测试员口述 + 截图，ReproForge：
- VL 看截图确认实际值 80；
- 生成 Playwright 测试，连跑 3 次稳定复现；
- 求最小复现（删无关步骤）；
- 输出 Issue（预期 160 / 实际 80 / 最小步骤 / 可疑 App.tsx）。

**场景 B：视频复现**
测试员上传一段录屏 + 语音，ReproForge 抽帧、ASR 转写、LLM 提取操作序列与口述，自动转成可运行测试。

**场景 C：冷启动（无历史）**
首次使用，记忆库为空，ReproForge 正常输出 Issue；后续相同类型 Bug 出现时，recall 检索历史辅助定位。

## 5. 功能需求

### 5.1 核心：6 节点流水线

| 节点 | 功能 | 降级 |
|---|---|---|
| **vision** | VL 看截图提 expected / actual / 页面状态 / 置信度 | 无截图 / 调用失败 → 跳过，走口述 |
| **evidence** | 综合口述 + 视觉，提 expected / actual，按置信度判是否需人工确认 | 低置信 → `needs_confirm` |
| **reproduction** | LLM 生成 Playwright 测试 → 连跑 3 次判稳定 → 最小复现 | 定位器失败 → 最多 2 轮自修复 |
| **recall** | RAG 检索历史相似 Bug（Top-3）注入 investigator | 库空 / 失败 → 无历史参考，照跑 |
| **investigator** | ripgrep + tree-sitter 检索 + LLM 打分，输出 Top3 可疑文件 | 无 ripgrep → 纯 Python 遍历 |
| **regression** | 审核 + 生成 Markdown Issue，并 ingest 进记忆库 | LLM 失败 → 确定性组装 Issue |

### 5.2 多模态输入

- 🖱️ **录制网页操作**：Playwright 监听 click / fill / goto，转 actions 序列；
- 🎬 **视频输入**：提音频（ASR）+ 抽帧 + LLM 提操作与口述；
- 🎤 **语音口述**：Gradio 录音 → ASR → 口述文本；
- ✍️ **手填**：JSON 操作 + 截图。

### 5.3 记忆与检索（RAG）

- 历史 Bug 入向量库（chromadb），文档 = 预期 + 实际 + 可疑文件 + testid；
- 新 Bug 检索 Top-3 相似历史，作为 investigator 的线索（不视为结论）。

### 5.4 模型层

- **本地为主 + 远程 fallback**：文本 / VL / embedding 三服务本地部署，远程 Stepfun API 作兜底；
- 业务代码经统一 OpenAI 兼容抽象，切换零改动。

## 6. 非功能需求

| 维度 | 要求 |
|---|---|
| **健壮性** | 任一节点 / 任一服务失败，主流水线仍输出 Issue（全降级链）|
| **可演示性** | 单人即可运行演示，每功能配降级兜底 |
| **本地部署** | 充分利用 DGX Spark 本地算力（GPU 服务 + CPU 服务）|
| **诚实边界** | 不宣称根因，只给可疑文件排序；复现稳定性由真实回放判定 |
| **性能** | 单 Bug 复现端到端在分钟级（Playwright 真跑占大头）|
| **可测试** | 单测全 mock，冒烟真调端到端验证 |

## 7. 范围

### 7.1 本期实现

- 6 节点线性流水线（LangGraph）；
- 四种输入（录制 / 视频 / 语音 / 手填）；
- VL 视觉、RAG 记忆（可独立开关 + 降级）；
- DGX Spark 三服务部署 + 远程 fallback；
- Gradio 步骤式 UI、商城跳转。

### 7.2 暂不做（路线图）

- 自动截图采集（接 capture / reproduction 失败截图）；
- CI / GitHub Actions 集成；
- 记忆库去重 / 过期 / 重排 / 混合检索；
- 多语言 / 多框架测试生成（当前 Playwright + TypeScript）。
