# ReproForge 架构与部署

> 大模型负责理解 Bug，Playwright 负责证明 Bug。
> 本文讲清楚两件事：**系统怎么跑**（6 节点的数据流，含 VL 视觉 + RAG 记忆）和**东西部署在哪**（双轨模型 + DGX Spark 本地算力）。

---

## 一、系统架构总览（数据流）

ReproForge 用 **LangGraph StateGraph** 把 6 个节点线性串联（vision → evidence → reproduction → recall → investigator → regression），输入是"截图(可选) + 操作 + 口述"，输出是"一份能直接提交的 Bug Issue"。

```
  截图(可选)    actions[]       segments[]        console[]
  (VL 视觉)   (Playwright      (faster-whisper    (browser
              录制操作)          语音转写)           console)
      │           │                  │                 │
      └────┬──────┴────────┬─────────┴─────────────────┘
           ▼               ▼
   ┏━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┓
   ┃         LangGraph StateGraph  (graph/workflow.py)       ┃
   ┃  START → ①vision → ②evidence → ③reproduction           ┃
   ┃       → ④recall → ⑤investigator → ⑥regression → END    ┃
   ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┛
       ① vision       ② evidence      ③ reproduction
        VL 看截图       综合口述+视觉     Playwright 连跑3次
        提expected/actual 提expected/actual 判稳定+最小复现
          │                │                │
       ④ recall       ⑤ investigator   ⑥ regression
        检索历史Bug       ripgrep+tree-sitter 审核+生成Issue
        (chromadb+bge)    +历史参考→Top3    →入记忆库
          │                │                │
          └━━━━━━━━━━━━━━━━┿━━━━━━━━━━━━━━━━┛
                           ▼
                 Gradio UI / 冒烟脚本
     复现结果摘要 · VL 视觉 · 生成的测试代码 · Bug Issue
```

**所有 LLM 调用**（各节点内部）都经过统一的 `llm/client.py`（OpenAI 兼容，含多模态 `chat_vision`），由 `PROFILE` 决定走远程 Stepfun 还是本地 vLLM——**业务代码零改动**（详见第四节）。VL 走远程 step-3.7 多模态；RAG 的 bge/chromadb 本地。**vision / recall 都是可选 + 降级**（任一关闭或失败，主流水线照跑）。

## 二、数据流逐步详解

### ⓪ vision · 视觉分析（`agents/vision.py`）— VL 多模态

- **输入**：`screenshot`（可选，UI 上传）+ 口述
- **做**：step-3.7 多模态看截图，提 `expected` / `actual` / `page_description` / `confidence`（`chat_vision`，content 含 `image_url`，本地文件转 base64 data URI）
- **降级**：无截图 / `REPROFORGE_VL=off` / 调用失败 → 空 `VisualFinding(used=False)`，evidence 照旧口述驱动
- **输出**：`VisualFinding`（喂给 evidence，按置信度优先合并；口述/视觉冲突 → `needs_confirm`）

### ① evidence · 证据分析（`agents/evidence.py`）

- **输入**：`actions`（操作）+ `segments`（语音）+ `console_log`
- **做**：
  1. 按时间戳把语音 segment 关联到最近的操作（`_nearest_segment`）→ 每个 action 带上 `user_narration`
  2. 启发式扫描口述里的异常指示词（"还是/不对/没变/应该/错误"…）→ 标 `suspected_anomaly`
  3. `chat_json` 让 LLM 从口述提取 `expected` / `actual` / `confidence`
- **降级**：`confidence < 0.6` → `needs_confirm=True`（转人工确认，不硬猜）
- **输出**：`BugTimeline{events, expected, actual, needs_confirm}`

### ② reproduction · 复现工程（`agents/reproduction.py`）——流水线最重的一环

- **输入**：`BugTimeline`
- **做**：
  1. `generate_test`：LLM 生成 Playwright (TS) 测试（`getByTestId` 定位 + 断言 expected）；`_strip_fence` 剥代码围栏、`_ensure_import` 补 import（**真跑前必需，mock 测不出**）
  2. 把 spec 写进被测项目目录（Playwright 要求 testDir 内 + cwd）
  3. **循环最多 3 次**（1 次初始 + 最多 2 轮修定位器）：
     - `run_n_times(spec, 3)`：连跑 3 次，`npx playwright test --reporter=json` 解析 JSON 报告判通过/失败
     - 3 次全失败（`stable_fail`）→ **稳定复现 Bug**，跳出
     - 全通过 → `no_bug`（Bug 没复现）
     - 否则 `fix_locator`（LLM 按报错修定位器，testid→role→placeholder 降级）重写再跑
  4. 稳定复现后 → 调 `minimize` 求最小复现
- **输出**：`ReproductionResult{success, spec_code, minimized, stable_rate="3/3", rounds, reason}`

> Bug 是不是真复现，是**跑出来的**（Playwright 真实回放 + 连跑 3 次判稳定），不是 LLM 嘴说的。

### ②.5 recall · 记忆检索（`agents/recall.py`）— RAG

- **输入**：`BugTimeline` + `actions`
- **做**：`memory/store.py`（chromadb 持久化 + bge-large-zh embedding）检索 Top-3 相似历史 Bug
- **降级**：`REPROFORGE_MEMORY=off` / 库空（首次跑）/ 失败 → 空 `HistoricalRef`，investigator 照旧
- **输出**：`HistoricalRef`（喂给 investigator，prompt 注入"相似历史 Bug 参考"段，仅作线索不视为结论）

### ③ investigator · 代码调查（`agents/code_investigator.py`）

- **输入**：`BugTimeline` + `console_errors` + `repo_path`
- **做**：
  1. `_extract_query_terms`：从 timeline 提检索词（testid、有区分度的值；**排除纯数字噪声**如 "2"/"160"）
  2. `code_search.search`：ripgrep 检索（不可用降级纯 Python 遍历），tree-sitter 提取命中所在**函数/组件名**作上下文，按命中数排序取 Top10
  3. `chat_json`：LLM 对每个候选文件打分（0–1）+ 一句话理由
- **诚实边界**：**不宣称根因，只给可疑文件排序**，取 Top3
- **输出**：`TopFiles{files[Top3], query_terms}`

### ④ regression · 回归审查（`agents/regression.py`）

- **输入**：`spec_code` + `BugTimeline` + `TopFiles` + `ReproductionResult`
- **做**：
  1. 结构字段确定性组装：`minimal_steps`（从最小复现结果转人类可读）、`stable_rate`、`suspected_files`
  2. `chat`：LLM 审核测试（断言是否对应 expected、选择器是否脆弱）+ 生成 Markdown Issue（标题/预期/实际/最小复现步骤/稳定率/可疑代码/截图）
- **降级**：LLM 失败 → `_fallback_body` 确定性组装 Issue
- **输出**：`Issue{title, expected, actual, minimal_steps, stable_rate, suspected_files, body}`

## 三、核心创新：最小复现算法（`minimization/minimize.py`）

纯确定性算法，**不依赖 LLM**——拿到能稳定复现的测试后，求出**最短稳定复现路径**。

```
原始步骤序列: [fill券, click应用, hover图片, click帮助, fill数量, click详情, ...]
                                    ↑候选可删      ↑候选可删        ↑候选可删
逐个尝试删除 → 用子集重新生成 spec 真跑 → Bug 仍在(passed=False)则永久删除，否则保留
重复直到无可删（最多 10 轮）
↓
最短稳定复现路径 + 稳定率仍 3/3
```

- `is_candidate_for_removal`：只删 `click/hover` 类无关步骤（含"个人中心/帮助/返回"等），**保留关键填写**（"优惠/券/数量/提交/加入购物车"等）
- 每次删一步就重跑验证——Bug 还在才真删，保证最小路径**仍能稳定复现**

> 开发拿到这个最小步骤，照着点几下就能复现 Bug，不用在十几步无关操作里找。

### 双轨切换机制（三处协同）

| 组件 | 作用 |
|---|---|
| `config.py` | `PROFILE=local` → 读 `LOCAL_BASE_URL`/`LOCAL_MODEL`/`LOCAL_API_KEY`；默认 → Stepfun 远程配置 |
| `llm/client.py` | OpenAI 兼容客户端单例。Stepfun 和本地 vLLM **都是 OpenAI 接口**，所以切换只换 `base_url`+`model`，业务代码一行不改 |
| `eval/compare.py` | 远程 vs 本地指标对比。切 PROFILE 时**必须重置 `llm.client._client=None`**，否则单例缓存旧 `base_url` 导致切换不生效 |

> ⚠️ **config 坑**：`config.py` 里 `PROFILE=local` 的默认值是 Ollama 的 `qwen2.5-coder:7b`（端口 11434），**不是** spark-71 的 vLLM。Demo 切本地时**必须用环境变量覆盖** `LOCAL_BASE_URL`/`LOCAL_MODEL`，指向 spark-71 的 vLLM endpoint。

```bash
# 开发期（默认远程 Stepfun，迭代快、不占本地显存）
python spike/smoke_phase3.py

# Demo / 评审期（切本地 vLLM）
# 1) 先在 spark-71 上起 vLLM（见下「vLLM 本地部署」）
# 2) 本地建 SSH 隧道，把 spark-71:8000 映射到本地
ssh -L 8000:localhost:8000 -p 6071 Developer@106.13.186.155
# 3) 切本地模型跑全流程（必须覆盖 LOCAL_BASE_URL / LOCAL_MODEL）
PROFILE=local \
LOCAL_BASE_URL=http://localhost:8000/v1 \
LOCAL_MODEL=/models/qwen36-35b-a3b \
python spike/smoke_phase3.py
```

### vLLM 本地部署（DGX Spark 实测，2026-07-21）

spark-71 上 vLLM 容器（`eugr/spark-vllm:latest`）+ 模型（`/home/Developer/models/qwen36-35b-a3b`，35B MoE fp8）均已就绪，**已实测启动成功并跑通推理**。

```bash
# 在 spark-71 上执行（host 网络，模型目录挂载）
docker run -d --name vllm --net=host --ipc=host --gpus all \
  --ulimit nofile=1048576:1048576 \
  -e VLLM_USE_DEEP_GEMM=0 \
  -v /home/Developer/models:/models \
  eugr/spark-vllm:latest \
  vllm serve /models/qwen36-35b-a3b --host 0.0.0.0 --port 8000 \
    --tensor-parallel-size 1 --gpu-memory-utilization 0.8 \
    --max-model-len 8192 --max-num-batched-tokens 4096 \
    --load-format fastsafetensors --kv-cache-dtype fp8 --enable-prefix-caching
```

**显存实测**（GB10 统一内存，标称 128GB / `free -h` 可用 119GB；`nvidia-smi` 的 Memory-Usage 显示 `Not Supported` 属正常，看 `free -h`）：

| `--gpu-memory-utilization` | vLLM 实际占用 | 留给系统 | 适用 |
|---|---|---|---|
| 0.4 | ~48 GB（按配置预估）| ~71 GB | 保守，多服务共存 |
| **0.8（Demo 用）** | **~100 GB（实测 `used 105Gi`）** | ~14 GB | 单服务，KV cache 充裕 |

> ⚠️ **关键坑：必须 `-e VLLM_USE_DEEP_GEMM=0`**。nightly vLLM（`v0.23.1rc1`）的 DeepGEMM 在 GB10 上做 fp8 MoE 权重预处理时，NVCC JIT 编译会失败：`RuntimeError: NVCC compilation failed (Bad file descriptor)`，容器启动 ~40 秒后 Exited。**不带这个环境变量就起不来**。禁用 DeepGEMM 后改走 Triton/FlashInfer 后端（启动多 1-2 分钟预热 kernel），稳定可用。模型是 reasoning 模型，推理输出会带 `thinking` 段，`llm/client.py` 的 `re.search(r'\{.*\}')` 已兼容。

## 六、对齐 NVIDIA Agent Toolkit 三层（路演加分）

NVIDIA 把 Agent 架构分成 `System of Models → Harness → Secure Runtime + Skills`。ReproForge 正好对齐：

| NVIDIA Agent Toolkit 层 | ReproForge 对应 |
|---|---|
| **System of Models** | 双轨模型：Stepfun step-3.7（远程）/ qwen3.6-35b（本地 vLLM），统一 OpenAI 兼容 |
| **Harness**（编排）| LangGraph StateGraph，串联 evidence→reproduction→investigator→regression，对齐官方 AI-Q Blueprint 的 "Intent → 子代理" 形态 |
| **Secure Runtime + Skills** | Playwright 沙箱（确定性回放，证明 Bug）+ ripgrep/tree-sitter（检索 skill）+ faster-whisper（ASR skill）|

> 路演时把架构图标注这三层 + "对齐 NVIDIA Agent Toolkit / AI-Q Blueprint"，评委立刻 get。

## 七、关键设计决策

1. **确定性底座优先**：Bug 是否复现由 Playwright 真跑决定，不靠 LLM 猜。LLM 只负责理解（提 expected/actual）和生成（写测试/打分/写 Issue）。
2. **降级链贯穿全程**：evidence 低置信→人工确认；reproduction 不稳定→2 轮定位器上限；code_search 无 ripgrep→纯 Python 遍历；regression LLM 挂→确定性 Issue。任何一环出问题，系统不崩。
3. **冒烟驱动**：4 个 mock 测试漏掉的真实 bug（代码围栏 / 漏 import / 路径正则 / 编码 / 测试产物污染）都由真调端到端冒烟发现——AI 写的代码必须真跑。
4. **诚实边界**：code_investigator 只排序可疑文件、不宣称根因；reproduction 用客观的"连跑稳定率"说话。
